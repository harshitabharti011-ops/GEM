\begin{abstract}
We extend NVIDIA's GEM boomerang-scheduled GPU logic simulator so that
DSP48E2, CARRY4 and SRLC32E primitives survive Yosys synthesis as word-level
cells and are evaluated natively on the GPU ALU, instead of being shredded into
1-bit AND-inverter logic. This document gives the modified levelization
equations that make a heterogeneous DAG schedulable, the VRAM layout that keeps
macro operands 64-bit aligned and coalesced, a measured occupancy and register
profile on \texttt{sm\_86}, an alignment invariant that variable-length
instruction sections must preserve, and a layered verification argument in
which each oracle's authority is bounded explicitly rather than assumed.
\end{abstract}

%======================================================================
\section{The Invariant That Macros Break}
%======================================================================

Stock GEM rests on a single structural invariant:

\begin{quote}
\emph{Every value inside a partition is produced by the AND-gate cover, and
reaches its consumers through the boomerang hierarchy.}
\end{quote}

Word-level macros violate it in three independent ways. A macro output is
produced by a separate evaluation phase, written into a separate buffer, on a
separate schedule. Each consequence had to be addressed explicitly, and the
equations in Section~\ref{sec:sched} exist precisely to restore a well-defined
order once the invariant no longer holds.

Concretely, in the kernel the boomerang stages of one partition communicate
through \texttt{shared\_state}, while the macro evaluation phase writes into
\texttt{shared\_writeouts}. These are different buffers. A macro result
therefore cannot become visible to boolean logic within the same partition at
all --- not in a later boomerang stage, not under any batching order. The only
ordering primitive strong enough is the cooperative grid synchronisation
between \emph{major} stages, and the scheduling equations are built around that
fact.

\section{Modified DAG Levelization Equations}
\label{sec:levelization}
\label{sec:sched}
%======================================================================

\subsection{Notation}

Let $G=(V,E)$ be the AND-inverter graph after macro-preserving synthesis. Each
$v \in V$ is an \emph{aigpin}. Write:

\begin{itemize}
  \item $\fanin(v)$ --- the AND-gate fan-in of $v$ (empty for non-AND nodes);
  \item $\mathcal{M}$ --- the set of macro instances;
  \item $\combin(m)$ --- the \emph{combinational} input pins of macro $m$
        (CARRY4: $S,DI,CIN,CYINIT$; SRLC32E: $A[4{:}0]$; DSP48E2: $\emptyset$);
  \item $\seqin(m)$ --- \emph{all} pins macro $m$ latches on the clock edge,
        including its clock enable;
  \item $\mathcal{O}_c \subset V$ --- aigpins driven by a \emph{combinational}
        macro output (CARRY4 $CO,O$; SRLC32E $Q,Q_{31}$);
  \item $\mathcal{O}_s \subset V$ --- aigpins driven by a \emph{clocked} macro
        output (DSP48E2 $P$).
\end{itemize}

We define two integer labels per node. They coincide everywhere except on
$\mathcal{O}_c$, and that single point of divergence is the entire content of
the heterogeneous schedule.

\begin{description}
  \item[$\avail(v)$] the major stage in which $v$'s value may be \emph{read} by
        boolean logic;
  \item[$\eval(v)$] the major stage in which the producer of $v$ is
        \emph{executed}.
\end{description}

\subsection{The equations}

\begin{align}
\avail(v) &= 0, &&
  \begin{aligned}
  &v \text{ a primary input, DFF } Q, \text{ SRAM read data,}\\
  &\text{or } v \in \mathcal{O}_s
  \end{aligned}
  \label{eq:leaf}\\[4pt]
\avail(v) &= \max_{u \in \fanin(v)} \avail(u), && v \text{ an AND gate}
  \label{eq:and}\\[4pt]
\eval(m)  &= \max_{p \in \combin(m)}
             \begin{cases}
               \eval(p) & p \in \mathcal{O}_c\\
               \avail(p) & \text{otherwise}
             \end{cases}, && m \in \mathcal{M}
  \label{eq:eval}\\[4pt]
\avail(v) &= \eval(m) + 1, && v \in \mathcal{O}_c \text{ driven by } m
  \label{eq:plusone}
\end{align}

Four properties follow, and each one is load-bearing.

\paragraph{(P1) Boolean depth is free.}
Equation~\eqref{eq:and} takes a maximum, never an increment. An arbitrarily
deep cone of AND gates evaluates inside one major stage, exactly as in stock
GEM. The boomerang hierarchy is untouched.

\paragraph{(P2) Clocked macro outputs cost nothing.}
By~\eqref{eq:leaf}, $\mathcal{O}_s$ is a level-0 leaf. A DSP's $P$ is read from
global state like a DFF's $Q$: what a reader observes this cycle is last
cycle's commit, which is the correct register semantics and requires no
boundary.

\paragraph{(P3) Macro-to-macro chaining costs nothing.}
The case split in~\eqref{eq:eval} takes $\eval$, not $\avail$, of an operand
that is itself a combinational macro output. Hence a CARRY4 chain of any length
--- $CO[3] \rightarrow CIN$, the dependency the problem statement names
explicitly --- resolves inside a single major stage. Ordering within the stage
is supplied by emitting one batch per chain link, separated by
\texttt{\_\_syncthreads()}. Without this case split a 64-bit carry-chain adder
would demand 16 major stages, and a wide datapath would exceed the kernel's
hard limit of 32.

\paragraph{(P4) Only macro-to-boolean pays.}
The $+1$ in~\eqref{eq:plusone} is charged exactly once, and only where a
combinational macro result must cross into the AND-gate domain. It is the
minimum price consistent with the buffer separation described in
Section~1.

\subsection{Stage construction}

Let $D = \max_{v} \eval(v)$ extended over endpoints. Major stage $j \in
[0,D]$ is then defined by:

\begin{align}
\text{endpoints}(j) &= \Bigl\{ e : \max_{p \in \text{inputs}(e)} \avail(p) = j \Bigr\}\\
\text{macros}(j)    &= \{ m \in \mathcal{M} : \eval(m) = j \}\\
\text{forward}(j)   &= \{ v : \eval(v) \le j \;\wedge\; \exists\, c \in
                       \text{consumers}(v),\ \eval(c) > j \}
\end{align}

$\text{forward}(j)$ becomes the staged I/O pin set of stage $j$ and the primary
input set of stage $j{+}1$. Its second clause is the subtle one: a node with
$\eval(v) = j$ but $\avail(v) = j{+}1$ --- that is, a combinational macro
output produced by stage $j$'s macro phase --- must be forwarded even though it
is not readable in the stage that produces it.

\paragraph{Regression guarantee.}
If $\mathcal{O}_c = \emptyset$ then $D = 0$ by construction, and the entire
macro-aware path is bypassed in favour of the unmodified level-split staging.
A macro-free netlist is therefore scheduled bit-identically to stock GEM. This
is what makes the baseline comparison in Section~\ref{sec:verif} meaningful
rather than circular, and it is asserted directly by unit test
\texttt{nothing\_but\_a\_combinational\_macro\_can\_raise\_a\_stage}.

\subsection{Measured instantiation}

On \texttt{synth/tests/macro\_smoke.sv} (2 DSP48E2, 4 chained CARRY4,
1 SRLC32E, plus ordinary RTL), the equations yield $D = 1$:

\begin{center}
\begin{tabular}{llr}
\toprule
Major stage & Contents & Boomerang depth\\
\midrule
0 & 4 CARRY4 (chained), 1 SRLC32E, 2 DSP48E2, 8 DFF, ordinary cone & 7\\
1 & primary outputs consuming macro results & 4\\
\bottomrule
\end{tabular}
\end{center}

The four chained CARRY4s all satisfy $\eval = 0$ by (P3), confirming that the
16-bit carry chain costs no additional grid synchronisation.

On the scaled benchmark \texttt{bench/macro\_bench.sv} at $\text{LANES}=16$
(16 DSP48E2, 64 CARRY4 in 16 four-block chains, 16 SRLC32E, 96 macros in all)
the equations again yield $D = 1$, and the 64 chained CARRY4s occupy
\emph{four batches within one major stage} rather than four stages:

\begin{center}
\begin{tabular}{llrr}
\toprule
Major stage & Contents & Partitions & Macro batches\\
\midrule
0 & 16 DSP48E2 (endpoint), 64 CARRY4, 16 SRLC32E & 2 & 5\\
1 & boolean cones consuming macro results & 1 & 0\\
\bottomrule
\end{tabular}
\end{center}

This is (P3) doing the work it exists for. Ordering within a chain is enforced
by \texttt{\_\_syncthreads()} between batches, which is free; only the
macro$\to$boolean edge costs a \texttt{this\_grid().sync()}. Had chaining been
charged a major stage per link, this design would have needed five instead of
two, and \S\ref{sec:results} shows that each additional major stage costs
$\approx 31\,\mu$s per simulated cycle --- so (P3) is worth roughly
$93\,\mu$s/cycle on a design this shape.

\section{VRAM Layout Architecture}
\label{sec:vram}
%======================================================================

\subsection{Two disjoint regions}

Macro state is split by lifetime, not by macro:

\begin{enumerate}
  \item \textbf{Bit-addressed outputs} live in the partition's write-out block,
        interleaved with ordinary boolean write-outs so that the existing
        commit path carries them to global state with no separate store.
  \item \textbf{Word-addressed internal state} --- a DSP's $PREG$, an SRLC32E's
        32-bit shift register --- lives in a dedicated
        \texttt{UVec<u64>} region, \texttt{macro\_word\_state}.
\end{enumerate}

\subsection{Write-out block ordering}

Within a partition the write-out region is ordered

\[
\underbrace{\text{normal}}_{n_w}
\;\Vert\;
\underbrace{\text{macro}}_{n_m}
\;\Vert\;
\underbrace{\text{duplicate}}_{n_d}
\;\Vert\;
\underbrace{\text{SRAM}}_{n_s}
\]

with SRAM deliberately last so its pre-existing offset arithmetic is untouched
and --- less obviously --- with the macro block \emph{below} the duplicates
rather than between them and the SRAMs. That ordering is a correctness
requirement rather than a layout preference; \S\ref{sec:dup-defect} gives the
defect that established it.

Macro instance $i$ receives

\[
n_{\text{slots}}(i) = \left\lceil \frac{|\text{outputs}(i)|}{32} \right\rceil
\quad\text{contiguous \texttt{u32} slots,}
\]

so bit $b$ of that macro lands at global state bit
$32 \cdot \text{macro\_start}_i + b$. Two consequences fall out of the
allocation rather than from a convention: every macro's output field is
contiguous, and its base is 32-bit aligned. Because each macro owns whole
words, no two macros can contend for the same \texttt{u32}, and the device-side
result scatter is a plain read-modify-write requiring \emph{no atomics}.

\subsection{Word-state region and 64-bit alignment}

\[
\text{state\_words}(k) =
\begin{cases}
1 & k = \text{DSP48E2} \quad (P[47{:}0])\\
1 & k = \text{SRLC32E} \quad (32\text{-bit SR})\\
0 & k = \text{CARRY4} \quad (\text{stateless})
\end{cases}
\]

The region is declared as \texttt{UVec<u64>}. The element type supplies 8-byte
alignment and \texttt{cudaMalloc} supplies a 256-byte aligned base, so the
problem statement's 64-bit alignment requirement holds \emph{structurally}
rather than by runtime assertion. Instances are grouped by kind and each kind
begins on a warp boundary, so a type-homogeneous batch reads a contiguous,
segment-aligned span --- the condition for coalesced access.

\paragraph{Measured layout (\texttt{macro\_smoke}).}

\begin{center}
\begin{tabular}{lr}
\toprule
Quantity & Value\\
\midrule
Macro instances & 7\\
Word-state region & 64 $\times$ \texttt{u64} = \textbf{512 bytes}\\
Alignment & 64-bit (verified)\\
Descriptor words & 458\\
Macro write-out slots & 9 \; (2 DSP $\times$ 2, 4 CARRY4 $\times$ 1, 1 SRL $\times$ 1)\\
\bottomrule
\end{tabular}
\end{center}

The 458-word descriptor total decomposes exactly as
$2(5{+}123{+}48) + (5{+}7{+}2) + 4(5{+}10{+}8) = 352 + 14 + 92 = 458$,
where each descriptor carries a 5-word header followed by input and output bit
positions. The exact agreement is used as a host-side structural check.

\subsection{Script-side indirection}

A batch record in the block script references macros by index into the layout's
slot table rather than inlining descriptors:

\begin{lstlisting}
32-bit boomerang stage index this batch runs AFTER
32-bit macro kind code
32-bit count
count x 32-bit slot index into the descriptor CSR
\end{lstlisting}

A DSP descriptor alone is 176 words; inlining would dwarf the script it lives
in. Measured effect on \texttt{macro\_smoke}: the macro-preserving script is
\textbf{69{,}652 words} against the shredded baseline's \textbf{94{,}720} --- a
26\,\% reduction, the direct instruction-memory dividend of not shredding.

\section{Occupancy and Resource Profile}
\label{sec:occupancy}
\label{sec:occ}
%======================================================================

Measured with \texttt{cuobjdump -res-usage} on the shipped \texttt{sm\_86}
binary, and with a device query for the machine parameters.

\begin{center}
\begin{tabular}{lr}
\toprule
\multicolumn{2}{c}{\textbf{Kernel} \texttt{simulate\_v1\_noninteractive\_simple\_scan}}\\
\midrule
Registers / thread & \textbf{86} and \textbf{105} \; (ceiling 128)\\

Local memory & \textbf{0 bytes} --- no spilling (both variants)\\
Shared memory & 3{,}328 bytes\\
Constant bank 0 & 440 / 408 bytes\\
\midrule
\multicolumn{2}{c}{\textbf{Device} --- NVIDIA RTX 3050 6\,GB Laptop, \texttt{sm\_86}}\\
\midrule
Streaming multiprocessors & 20\\
Registers per SM & 65{,}536\\
Register allocation granularity & 256 per warp\\
Blocks per SM at 86 reg/thread & 2\\
Blocks per SM at 105 reg/thread & 2\\

\bottomrule
\end{tabular}
\end{center}

The fatbin carries two compiled variants of the kernel, at 86 and 105 registers
per thread. Which one the driver loads is not determined here, and it does not
need to be: both round to the same occupancy. At 256 threads per block, a warp
allocates $\lceil 86 \cdot 32 / 256 \rceil \cdot 256 = 2816$ registers, a block
$8 \times 2816 = 22{,}528$, and $\lfloor 65536 / 22528 \rfloor = 2$ blocks per
SM. The 105-register variant gives 2 as well. Every conclusion below is
therefore insensitive to the choice.

\paragraph{The 3-blocks/SM threshold, and how narrowly it is missed.}
Three resident blocks would need $\lfloor 65536/3 \rfloor = 21{,}845$ registers
per block, i.e.\ $2730$ per warp, which the 256-register granularity rounds down
to $2560$ --- exactly $\mathbf{80}$ registers per thread. At 86 the kernel
misses the threshold by six registers per thread, or $512$ registers per SM out
of $65{,}536$: under one percent. Capping at
\texttt{-maxrregcount=80} would raise the cooperative grid ceiling from 40 to
$3 \times 20 = 60$ blocks, a fifty percent increase in resident parallelism.

That lever is recorded rather than exercised, and \S\ref{sec:throughput}
explains why it would change nothing on the present benchmark: at
$\text{LANES}=16$ the macro-preserving flow produces three partitions, so it
occupies at most two blocks. Raising a ceiling of 40 to 60 cannot help a
workload that is using two. The measurement identifies the lever; a design with
enough partitions to press against the ceiling is what would make it pay.

\subsection{Why the ceiling is a design boundary}

\texttt{build.rs} pins \texttt{-maxrregcount=128}. At 256 threads per block this
admits exactly 2 blocks/SM, giving a cooperative grid ceiling of 40 --- which is
\emph{identical} to \texttt{usage.md}'s recommended $2 \times \text{SM count}$.
There is no headroom: the advisory figure and the hardware limit are the same
number.

The occupancy consequence is therefore not a launch failure. Because
\texttt{-maxrregcount} \emph{caps} allocation rather than permitting growth,
additional register pressure in the macro phase does not fail to launch --- it
\textbf{spills to local memory and silently loses throughput}. Launch success
proves nothing about occupancy health. The metric that does is

\begin{center}
\texttt{l1tex\_\_t\_sectors\_pipe\_lsu\_mem\_local\_op\_ld.sum}
\end{center}

under Nsight Compute --- or, without profiling privileges,
\texttt{cuobjdump -res-usage}, which reports the same fact statically as
\texttt{LOCAL} and \texttt{STACK}. Both variants of the shipped kernel report
\texttt{STACK:0 LOCAL:0}, so the macro phase is inside budget with 22 registers
of headroom against the 128 cap. That margin is the reason the correctness
fixes could be made without measuring occupancy after each one --- but it is
not licence: richer DSP modes or chain fusion should be assumed to cross it and
must be re-measured, not estimated.

It is worth recording that this figure improved as a side effect of a
correctness fix rather than a tuning pass. Moving the \texttt{data\_inv}
correction ahead of the macro phase (\S\ref{sec:latent}) replaced two XOR
operations with one and removed a value that had been live across the entire
phase: registers fell from 125 to 86, still with no spilling.

\paragraph{Design consequence.}
This boundary is why the correctness fixes described in
Section~\ref{sec:verif} were implemented \emph{host-side}, in the scheduler and
memory formatter, rather than in \texttt{csrc/kernel\_v1\_impl.cuh}. Every one
of them adds zero registers.

%======================================================================
\section{Dual-Oracle Verification Methodology}
\label{sec:verif}
%======================================================================

The problem statement supplies no golden reference model. We therefore
construct two independent oracles and apply each only where it has authority.
The central discipline is that \textbf{an oracle must share no code with the
thing it validates}.


\subsection{The script alignment invariant}
\label{sec:align}

Injecting variable-length macro batches into GEM's VLIW-style script stream
uncovered an undocumented structural constraint.

The boomerang sections are not read word by word. They are fetched with vector
loads:

\begin{lstlisting}
struct alignas(8)  VectorRead2 { u32 c1, c2; };
struct alignas(16) VectorRead4 { u32 c1, c2, c3, c4; };
t4_1.read(((const VectorRead4 *)(script + script_pi)) + threadIdx.x);
\end{lstlisting}

The cast to \texttt{VectorRead4*} requires \texttt{script\_pi} to be a multiple
of four \texttt{u32} words. Stock GEM satisfies this without ever stating it:
the metadata block is 256 words, each global-read round is $256 \times 2$, and
each boomerang stage is $256 \times 4 \times 5$. Every constituent is a
multiple of four, so the invariant holds by construction and no code asserts
it.

The macro section is the first variable-length element ever added to the
stream. A batch record is $3 + \mathrm{count}$ words, so \emph{any batch with
an even count breaks the alignment for every partition that follows it}:

\begin{center}
\begin{tabular}{lrrl}
\toprule
Macro section contents & Batches & Words & $\equiv 0 \bmod 4$?\\
\midrule
4 CARRY4 + 1 SRLC32E, all $\mathrm{count}=1$ & 5 & 20 & yes\\
\quad + 1 DSP48E2 batch, $\mathrm{count}=2$ & 6 & \textbf{25} & \textbf{no}\\
\bottomrule
\end{tabular}
\end{center}

The failure mode is instructive. It is not a wrong answer and not an illegal
address; it is \texttt{CUDA\_ERROR\_MISALIGNED\_ADDRESS}, raised at the
cooperative launch's synchronisation point, naming neither the script nor the
macro that caused it. It was identified by the distinction between
\emph{misaligned} and \emph{illegal}: an illegal address would have implicated
descriptor indexing, whereas misalignment can only come from a widened load.
That the fault was identical at 2 blocks and at 40 excluded any block-count
dependence.

The fix is host-side, in the script emitter, and costs no registers:

\begin{lstlisting}
while script.len() % 4 != 0 { script.push(0); }
\end{lstlisting}

We record this as a general design rule for the architecture: \textbf{any
variable-length section spliced into a GPU instruction stream consumed by
widened loads must preserve the widest load's alignment}, and that requirement
should be asserted at emission rather than discovered at launch.

\subsection{What each oracle can and cannot establish}

The three oracles are not interchangeable, and the distinction is not academic
--- each has produced a false or incomplete verdict in this project.

\begin{center}
\begin{tabular}{p{3.1cm}p{5.0cm}p{5.4cm}}
\toprule
Oracle & Establishes & Cannot establish\\
\midrule
CPU reference\newline(\texttt{--check-with-cpu}) &
\emph{Implementation fidelity}: the GPU kernel computes what GEM's own CPU
model computes, from the same script &
\emph{Design correctness}. Both sides consume the same mapped script, so a
synthesis or mapping defect appears identically in both and passes\\[4pt]
Shredded baseline VCD &
\emph{Cross-implementation agreement}: the macro path and a macro-free path
that shares no code with it agree &
Correctness of the baseline itself. It inherits every synthesis and mapping
defect of the shredded flow\\[4pt]
Design-level Python testbench &
\emph{Semantic correctness} against IEEE 1800--2012 SystemVerilog intent,
independent of both flows &
Nothing --- but only once calibrated against a known-good signal\\
\bottomrule
\end{tabular}
\end{center}

\subsection{Oracle 1 --- CPU reference, for the boolean path}

GEM ships a CPU simulator, invoked with \texttt{--check-with-cpu}. It is a
legitimate oracle for the shredded baseline, which contains only AND-inverter
logic and flip-flops, and the baseline passes it. Its authority is bounded,
however: it compares two implementations of the \emph{same script}, so it
validates that the GPU is faithful to the CPU model, not that either is
faithful to the RTL.

It is \emph{not} an oracle for the macro path, and treating it as one produced
the most instructive failure of this project. At one point the native run
reported \texttt{sanity test passed} while every macro-driven output in the
VCD was frozen at its initial value for all 2001 cycles. The CPU reference does
not model macro semantics, so it agreed with the GPU about bits that neither
was computing. Two errors cancelled, and a green result concealed a completely
dead datapath.

\subsection{Oracle 2 --- shredded-baseline VCD, for the macro path}

The macro-preserving and shredded builds are the \emph{same RTL} driven by the
\emph{same stimulus}. The shredded build is independently validated by
Oracle 1. Their output waveforms must therefore agree at every timestamp on
every port. Crucially, the shredded path exercises no macro code whatsoever:
the two share no implementation, so agreement is evidence and not tautology.

\texttt{bench/compare\_vcd.py} performs this comparison by port name (VCD
identifier codes are per-file and meaningless across files), reporting ports
present in only one file separately rather than silently ignoring them. The
comparator itself is validated in both directions: it passes on identical input
and detects a deliberate three-bit mutation.

This oracle immediately localised what Oracle 1 had missed --- 110 of 123 ports
differing, partitioned cleanly by macro kind --- and each subsequent fix moved
a specific port group from differing to matching.

\paragraph{Establishing that the baseline is trustworthy.}
A cross-implementation oracle is only as good as the reference implementation,
so the baseline was itself validated against a third, independent simulator:
GEM's \texttt{naive\_sim}, which evaluates the gate-level netlist directly on
the CPU with no script, no partitioning and no boomerang scheduling. It shares
essentially no code with the GPU path.

\begin{center}
\begin{tabular}{lr}
\toprule
Comparison (400 cycles, 123 ports) & Ports differing\\
\midrule
\texttt{naive\_sim} vs shredded GPU & \textbf{0 / 123}\\
\texttt{naive\_sim} vs macro-preserving GPU & 108 / 123\\
\bottomrule
\end{tabular}
\end{center}

The shredded GPU run is bit-exact against netlist-level ground truth on every
port. The baseline is therefore sound, and a disagreement reported by Oracle 2
is attributable to the macro path.

\paragraph{A retracted inference, recorded deliberately.}
An earlier draft of this report asserted that the baseline was defective on
\texttt{sum[16]}, reasoning that the carry-out of a 16-bit addition cannot be
constant under pseudo-random stimulus, whereas the shredded waveform records
one value change in 2001 cycles. \texttt{naive\_sim} reproduces that same
constant from the netlist. The netlist behaviour is what it is; the faulty step
was reasoning from RTL intent \emph{across} a synthesis boundary that had not
been verified. We record the retraction rather than silently deleting it,
because it is the same class of error the methodology exists to catch: a
confident inference that no measurement supported.

\subsection{Oracle 3 --- design-level Python testbench}

\texttt{bench/golden\_model.py} evaluates \texttt{macro\_smoke.sv}'s RTL
semantics directly in Python from the same input VCD, sharing no code with
either synthesis flow or with the simulator. It is the only oracle that
validates against \emph{design intent} rather than against another
implementation, and it is what attributes a disagreement to one side or the
other.

\paragraph{Status: authored, not yet calibrated.}
The model does not currently reproduce \texttt{scratch}
($\mathtt{cnt} \oplus \{x[3{:}0], y[3{:}0]\}$), a macro-free signal that
Oracle 1 has already validated. A model that disagrees with a known-good
signal is wrong about that signal, so its verdicts on the macro-driven ports
are withheld. Calibration was attempted over input-sample offsets
$\pm 2$ cycles, both nibble orderings, and all 256 counter phases; the best fit
was 14 of 30 cycles, indistinguishable from chance. The mismatch is therefore
structural --- in how GEM's cycle indexing maps onto the generated stimulus ---
rather than a parameter to be swept. \textbf{Calibrating on \texttt{scratch} is
the prerequisite for every remaining correctness claim in
Section~\ref{sec:results}.}

We state this rather than presenting an uncalibrated model as evidence: the
methodological point of this section is that an unvalidated oracle is worse
than none, and the same standard applies to our own.

\subsection{Oracle 4 --- cross-language macro models}

For the primitive models themselves (Deliverable C) the oracle is two
independent transcriptions of the problem statement's equations, in C++
(\texttt{csrc/macros.cuh}, compiled both as host code and as \texttt{\_\_device\_\_}
code) and in Python (\texttt{csrc/tests/reference\_model.py}), diffed bit for
bit over an identical vector set:

\begin{center}
\begin{tabular}{lr}
\toprule

\subsection{Throughput}
\label{sec:throughput}

\texttt{macro\_bench} at $\text{LANES}=16$. Same GPU, same stimulus, same
\texttt{num\_blocks} $=40$, same 400 cycles, same binary; five repetitions per
side, median reported. Timing is GEM's own \texttt{simulation} span, which
brackets the kernel launches and excludes parsing, mapping and VCD writing.

\begin{center}
\begin{tabular}{lrrrr}
\toprule
Configuration & Median & Cycles/s & Script/cycle & Per cycle\\
\midrule
Shredded baseline & 18.65\,ms & \textbf{21{,}445} & 2{,}060.0\,KiB & 46.6\,$\mu$s\\
Native macros     & 31.09\,ms & \textbf{12{,}866} &   454.5\,KiB & 77.7\,$\mu$s\\
\midrule
Ratio             & & $\mathbf{0.60\times}$ & $\mathbf{4.53\times}$ smaller & $+31.1\,\mu$s\\
\bottomrule
\end{tabular}
\end{center}

\paragraph{The optimisation succeeds on its own metric and loses on wall clock.}
GEM re-reads its entire instruction script from global memory on every
simulated cycle, so script size is the per-cycle DRAM traffic floor and is
exactly the quantity this work attacks. It fell $4.53\times$, from 527{,}360 to
116{,}340 \texttt{u32} words. Runtime nevertheless rose by $31.1\,\mu$s per
cycle. Both statements are measurements; neither is qualified.

\paragraph{Therefore the workload is not bandwidth-bound.}
This is the load-bearing inference, and it is falsifiable rather than
rhetorical. The native configuration reads $1.64$\,MB \emph{less} every cycle.
Were the run limited by script bandwidth, its script-read component would have
fallen to $22\,\%$ of the baseline's and total runtime would have fallen with
it. It rose. Expressing the same data as achieved script-read rates makes the
gap plain:

\begin{center}
\begin{tabular}{lrrr}
\toprule
Configuration & Script traffic & Elapsed & Achieved rate\\
\midrule
Shredded baseline & 843.8\,MB & 18.65\,ms & 45.2\,GB/s\\
Native macros     & 186.1\,MB & 31.09\,ms & \textbf{6.0\,GB/s}\\
\bottomrule
\end{tabular}
\end{center}

At $6.0$\,GB/s the native path is nowhere near the memory system's limit. It is
waiting on something else.

\paragraph{Two candidate causes, and they are separable.}
\emph{(i) The additional major stage.} Macro-depth staging places boolean
consumers of a macro result one major stage above their producer, so the native
path executes two \texttt{this\_grid().sync()} per cycle against the baseline's
one. A grid barrier of $\approx 31\,\mu$s is the right order for this part.

\emph{(ii) Partition-count collapse.} GEM's unit of parallelism is the
\emph{partition}, and the front-end table above shows the native flow needs
three where the baseline needs six --- and splits them across two sequential
stages, so at most two blocks are resident at any instant. With
$\texttt{num\_blocks}=40$ both configurations badly under-fill the device, but
the native one under-fills it by a further factor of three.

Cause (ii) is the more interesting of the two, because it is not an
implementation defect but a structural tension in the approach:
\textbf{fewer cells means fewer partitions means less parallelism.} The script
saving is real, and it only pays once the design is large enough that both
flows still produce many partitions. This reframes what a larger benchmark
tests --- not whether the script shrinks, which is settled, but whether
partition count survives the shrinking.

Section~\ref{sec:profile} reports the Nsight Compute measurement that
discriminates between (i) and (ii).

\paragraph{What this result is not.}
It is not evidence that native macro evaluation is a bad idea, and it is not a
speedup. It is a measurement of where the crossover is not yet. The honest
summary is that at $\text{LANES}=16$ on an RTX 3050 Laptop, the design is too
small for a $4.53\times$ bandwidth saving to outweigh one extra grid barrier
and a threefold loss of occupancy.

\subsection{Defects the ladder exposed}
\label{sec:latent}

Every one was silent: correct-looking execution, wrong arithmetic, no
diagnostic anywhere.

\paragraph{Write-out polarity.}
A write-out slot stores the value of \texttt{pin\_iv}, which for an inverted
pin is the complement of the AND-gate cover's raw result; the \texttt{data\_inv}
table restores it at commit. The macro phase ran \emph{before} that correction
and therefore read every inverted operand backwards --- observed as an exact
whole-vector inversion on a CARRY4's \texttt{O} outputs. The correction now
applies to \texttt{shared\_writeouts} in place, ahead of the macro phase; macro
results are written afterwards and carry \texttt{data\_inv} $=0$, so they are
correctly left alone.

\paragraph{Constant-one operands.}
In the AIG's \texttt{iv} encoding both constants live on aigpin 0:
$\mathtt{iv}=0$ is false and $\mathtt{iv}=1$ is \emph{true}. The formatter
mapped both to the ``no bit'' sentinel, which reads as zero. A DSP instantiated
with \texttt{.USE\_PREADD(1'b1)} therefore never applied its pre-adder, and one
with \texttt{.MODE(2'd1)} silently became mode~0 --- bypass instead of
multiply. One line, two unrelated-looking symptoms, no error at any point.
\texttt{macro\_layout::CONST\_ONE} is now a distinct sentinel honoured by the
formatter, the CPU executor and \texttt{GEM\_RD\_BIT} alike.

\paragraph{Duplicate write-outs landing in the macro block.}
\label{sec:dup-defect}
The kernel materialises the duplicate write-out words at

\[
\texttt{shared\_writeouts}\bigl[\,n_{io} - n_s - n_d + i\,\bigr],
\]

locating the block by subtracting from the \emph{top} of the write-out region.
Under stock GEM's layout, $\text{normal} \Vert \text{duplicate} \Vert
\text{SRAM}$, that expression evaluates to $n_w$ and is correct by
construction. Inserting the macro block between the duplicates and the SRAMs
shifts it up by $n_m$ words: every duplicate is then written \emph{inside the
macro block}, and the slots the host actually assigned retain whatever the
boomerang left in them.

Nothing detects this. All positions remain in range, so the host-side bounds
assertion passes; the macro phase subsequently overwrites the clobbered macro
words with correct results, so macro \emph{outputs} still verify. Only operands
\emph{read} through a duplicate slot are wrong --- that is, only pins a macro
requires in the opposite polarity from the one the AND-gate cover produced.

The symptom was correspondingly strange. On \texttt{macro\_bench}, CARRY4
blocks~2 and~3 were exact and blocks~0 and~1 were wrong. Bits $8$--$15$ lie
above the reach of the per-lane perturbations, so all sixteen lanes there share
one signal in one polarity and need no duplicate; the low blocks need both
polarities of $x$ and $x \oplus y$. The error injected at the block-1 boundary
then propagated up the carry chain with a per-bit halving decay, which reads
convincingly as an arithmetic bug in the CARRY4 model --- where nothing was
wrong.

The fix reorders the region to $\text{normal} \Vert \text{macro} \Vert
\text{duplicate} \Vert \text{SRAM}$, restoring the invariant the kernel already
assumes. Two lines in \texttt{flatten.rs} and \textbf{no kernel change}, which
matters directly: teaching the kernel about $n_m$ would have cost a metadata
word and a live value against the register budget of \S\ref{sec:occupancy}.

\subsection{What the harness must guarantee}

Two of this project's longest debugging episodes were not defects in the
simulator at all. They are worth recording because both are structural traps
that any GPU-simulator project can fall into, and both are now prevented by
construction rather than by remembering.

\paragraph{A \texttt{.gemparts} file is a build product, not an input.}
It serialises each partition's stages \emph{and its macro batches}, so it
encodes a snapshot of the scheduler in \texttt{pe.rs}. Changing the scheduler
and reusing the file causes the simulator to faithfully execute the old
schedule. One such run presented sixteen DSP48E2 instances that were endpoints,
held state slots and committed every cycle --- and were never once scheduled
into a batch, so \texttt{gem\_dsp48e2} was never called. Nothing reports that;
the accumulators simply never move.
\texttt{bench/verify\_ladder.sh} now re-maps both flows itself.

\paragraph{A successful build is not proof the binary is current.}
\texttt{Cargo.toml} declares \texttt{required-features = ["cuda"]} on
\texttt{cuda\_test}. Cargo \emph{skips} a binary whose required features are
absent --- silently, with exit status~0. A plain \texttt{cargo build --release}
therefore relinks \texttt{naive\_sim}, \texttt{flatten\_test} and
\texttt{cut\_map\_interactive}, leaves \texttt{cuda\_test} untouched, and
reports success. Successive fixes were then evaluated against a stale kernel
binary, producing a rung-3 failure whose mismatch counts were \emph{identical
to the digit} across 32{,}800 comparisons on twelve ports --- which is what
finally identified the cause, since no code change can leave a wrong answer
bit-for-bit unchanged. The ladder now builds with \texttt{--features cuda} and
additionally refuses to run if any file under \texttt{src/}, \texttt{csrc/},
\texttt{build.rs} or \texttt{Cargo.toml} is newer than the binary.

The general principle is the one this whole section argues: a verification
harness that can report a result it has not actually established is worse than
no harness, because it converts an absent measurement into a confident wrong
one.
